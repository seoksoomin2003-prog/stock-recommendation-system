# 실행 안정성 점검 (2026-11-15)

사용자 지시("전체코드 살펴보고 실행 안정성과 내 맥북에서의 안정성을 보완할 수 있는 부분을 찾아봐")로 점검했다. 점검 자체는 찾기만 했다. 그 뒤 사용자 지시로 1차 묶음 13개를 고쳤고, 아래 '1차 묶음 적용' 절에 적었다. 2차 묶음은 그대로다.

## 어떻게 봤나

- 코드를 세 영역으로 나눠 내용을 모르는 검토자 셋에게 따로 맡겼다: (1) 일일 작업과 자동 실행, (2) 서버와 파일 저장, (3) 외부 자료 호출.
- 맥북의 실행 환경은 직접 봤다: 자동 실행 설정, 로그, 디스크, 메모리, 전원 설정, 백업, 설치된 패키지.
- 아래에서 **[확인]**은 검토자의 지적을 내가 코드나 기록으로 다시 확인한 것, **[검토자]**는 검토자가 코드 경로를 추적했다고 보고했지만 내가 다시 확인하지 않은 것이다.
- 대상 기기: MacBook M2, 메모리 8GB, 디스크 여유 21GB(90% 사용).

## 결론

**당장 멈추는 문제는 없지만, 고쳐야 할 것이 분명히 있다.** 가장 중요한 것은 세 가지다.

1. **서버가 하루 넘게 켜져 있으면 종목 조회가 예전 시장 상태와 예전 기준일로 계산되는데 화면에는 최신으로 표시된다**(A1).
2. **일일 작업의 한 단계가 제한 시간에 8~12분밖에 여유가 없다**(B1). 오늘 추가한 예측 기록이 그 단계 안에서 돈다.
3. **맥이 잠들거나 작업이 중간에 죽으면 잘린 파일이 남고, 읽는 쪽이 그 오류를 잡지 못하는 곳이 있다**(C1).

## E. 작은 것

- **E1 [확인]** 브라우저가 먼저 연결을 끊은 것(`BrokenPipeError`)이 서버 오류 로그에 오류로 쌓인다. 진짜 오류가 묻힌다(`data/terminal/logs/server_errors.log`).
- **E2 [확인]** 내부에서 난 `ValueError`가 로그 없이 400 응답이 된다(`terminal/server.py:253`). 깨진 파일 같은 내부 문제가 입력 오류처럼 보인다.
- **E3 [검토자]** 야후에 실적 일정이 없는 한국 종목 약 200개를 스캔마다 다시 묻는다(빈 응답을 저장하지 않음). 요청 거절(429) 뒤에도 남은 종목을 계속 묻는다.
- **E4 [검토자]** SEC 호출 속도 제한이 프로세스마다 따로라, 아침 스캔 중에 화면을 쓰면 합쳐서 초당 10회를 넘을 수 있다. 거절(403)을 받아도 쉬지 않는다.
- **E5 [검토자]** P6 스캔에서 SEC의 일시적 실패가 20시간 저장된다(`data/loader.py:681`).
- **E6 [검토자]** KRX 응답 해석이 예외 처리 밖에 있다(`terminal/qsf/krx_history.py:100-109`). 로그인 페이지 같은 HTML이 오면 단계가 죽는다.
- **E7 [확인]** 이 프로그램 것이 아닌 잠자기 방지 프로세스가 맥을 계속 깨워 두고 있다: `caffeinate -d`가 5일째, 다른 프로젝트(`horizon_bot_beta`)의 것이 16시간째. 배터리가 닳는다. 이 프로그램의 일일 작업은 실행 중에만 깨워 두고 끝나면 놓는다.
- **E8 [검토자]** 실행 중 판단을 프로세스 번호만으로 한다(번호가 재사용되면 "이미 실행 중"). 자동 실행 재설치가 끝나기 전에 다시 올리면 등록이 빠질 수 있다. 둘 다 가능성 낮음.

## 살펴보고 문제없다고 본 것

- **이중 실행:** 일일 작업의 잠금은 프로세스가 죽으면 저절로 풀린다. 낡은 잠금도, 두 번 도는 일도 없다.
- **멈춤:** 모든 네트워크 호출에 제한 시간이 있고 재시도는 횟수가 정해져 있다. 단계마다 45분 또는 90분 제한이 있다.
- **단계 격리:** 한 단계가 실패해도 뒤 단계는 돈다. 텔레그램 알림은 전달될 때까지 다시 보낸다.
- **저장:** 포트폴리오·모의 매매 일지는 잠금과 fsync가 있고 잘린 줄을 "깨짐"으로 읽는다. 캐시, 관심종목, 설정, 최신 스캔 파일은 임시 파일에 쓰고 바꾼다.
- **서버:** 요청마다 스레드로 처리하고, 처리 중 예외는 500으로 돌려주며 서버가 죽지 않는다. 죽으면 launchd가 30초 간격으로 다시 올린다.
- **기록:** 점수 장부 두 시장, 추적 장부 두 시장, 전향 기록 15개의 해시 연결이 모두 OK다(오늘 확인).
- **패키지:** 버전이 고정돼 있고 충돌이 없다(`pip check`).
- **로그:** 일일 로그 10일에 160KB, 자동 실행 로그 23KB. 정리하지 않아도 될 크기다.
- **열쇠 노출:** 텔레그램, ECOS, DART, KRX 오류는 종류나 상태 코드만 남긴다.

| C1 | 한국 가격 파일(`bars_KR.json.gz`)과 한국 가격 캐시를 임시 파일에 쓴 뒤 바꾼다. 읽는 쪽은 잘린 압축 파일을 "자료 없음"으로 처리하고, 캐시는 다시 받는다. |
| C2 | 한국 KRX 가격 묶음을 다시 만들 때 잠금을 잡고 프로세스마다 다른 임시 파일을 쓴다. 기다린 쪽은 다시 만들지 않고 결과를 읽는다. |
| C3 | 전향 기록 저장소에 쓰기 잠금을 넣었다(`write.lock`). |
| C4 | 색인의 마지막 줄이 잘렸으면 그 앞의 줄은 계속 읽고, 검사는 "깨짐"으로 보고하며, 새 기록은 쓰지 않고 오류를 낸다(잘린 줄 뒤에 이어 쓰면 두 줄이 영영 붙는다). 색인에 쓴 줄은 디스크에 바로 밀어 넣는다. 점수 장부와 상위 3개 기록도 같다. **잘린 줄을 자동으로 지우지는 않는다.** 기록 파일이라 손으로 확인하고 고칠 일이다. |
| C5 | 캐시에 쓰지 못해도 방금 받은 자료는 돌려준다. |
| D3 | 한국 가격 캐시에서 최근 3개 구간보다 오래된 파일을 일일 작업의 캐시 정리 때 함께 지운다. 이름이 규칙에 맞는 파일만 지운다. 다음 일일 작업에서 23개(약 67MB)가 지워진다. 실행 기록은 자기 사본을 따로 갖고 있어 영향이 없다. 쓰는 중에 죽은 프로세스가 남긴 임시 파일도 하루가 지나면 같이 지운다. |
| E1 | 브라우저가 먼저 끊은 연결은 오류 로그에 쌓지 않는다. |
| E2 | 저장된 파일을 해석하지 못한 경우는 400이 아니라 500으로 기록한다. 입력이 잘못된 경우(400)도 로그에 한 줄 남긴다. |

**바뀐 동작 두 가지.**
- 실패한 단계가 같은 실행 안에서 한 번 더 돈다. 계속 실패하는 단계는 한 시간에 한 번이 아니라 두 번 시도된다. 알림은 전과 같이 내용이 바뀔 때만 간다.
- 색인이 잘렸을 때 전에는 모든 화면이 예외로 멈췄다. 이제는 화면은 뜨고 "깨짐"이 표시되며 새 기록만 멈춘다.

**확인한 것과 확인하지 못한 것.** 전체 시험이 통과했고, 서버를 다시 띄워 종목 조회와 기록 단계를 실제로 돌려 봤다. 맥이 실제로 잠들었다 깨는 상황, 디스크가 실제로 가득 찬 상황, 두 프로세스가 실제로 동시에 묶음을 다시 만드는 상황은 만들어 보지 않았다(시험은 그 조건을 흉내 낸 것이다).

## 보지 않은 것

- 과거 시험용 연구 모듈(`research_*`)과 옛 연구 패키지(`alpha_engine`)는 일일 작업과 서버가 쓰지 않아 깊이 보지 않았다.
- 검토자의 메모리 추정(D1, D2)은 만든 자료로 잰 값이다. 실제 장부로 재지 않았다.
- [검토자] 표시 항목은 고치기 전에 다시 확인해야 한다.
